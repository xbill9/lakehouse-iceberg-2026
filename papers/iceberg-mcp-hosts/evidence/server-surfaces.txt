A 405 here means the URL exists and refuses GET. It is not evidence that auth
works, and it is not evidence the tools are reachable -- only that the host is
answering. Both remote servers still need OAuth/IAM through the CLI host.

## Can the surface express "which version did I read?"

Retrieved from Google's own documentation via Developer Knowledge on 2026-09-16.
Sources:
  https://docs.cloud.google.com/bigquery/docs/reference/mcp
  https://docs.cloud.google.com/bigquery/docs/reference/mcp/tools_list/get_table_info
  https://docs.cloud.google.com/bigquery/docs/reference/mcp/tools_list/list_table_ids
  https://docs.cloud.google.com/bigquery/docs/use-bigquery-mcp

Q6 asks for the exact table version, by snapshot id or metadata location. Whether
a surface can answer it at all is a property of the surface, so it is read from
documentation first, exactly as `answers_rows` was.

bigquery-mcp   tool list: list_dataset_ids, get_dataset_info, list_table_ids,
                          get_table_info, execute_sql_readonly, execute_sql
               get_table_info returns table metadata and carries a
               `biglakeConfiguration` object for Apache Iceberg, but the
               documented output does **not** include a snapshot id, a metadata
               file location, or a table version.
               list_table_ids returns ids only.
               execute_sql can reach metadata if the caller knows the right
               INFORMATION_SCHEMA syntax, but the documentation names no
               INFORMATION_SCHEMA view or table option that exposes Iceberg
               snapshot ids or metadata locations for BigLake Iceberg tables.
               cites_version: NO, on the documented surface.

  Stated precisely: this is absence in the retrieved documentation, not a proof
  of impossibility. It is the same standard paper 1 used -- "declared" means
  named in the docs, and an undocumented path is not a served one. If a run finds
  a host citing a real snapshot id through this server, that is a finding and
  this line is what it contradicts.

morristai       namespaces, tables, table_schema, table_properties.
                table_properties can carry Iceberg table properties, which is
                the only candidate; whether the current metadata pointer appears
                there is NOT established from the documentation.
                cites_version: UNKNOWN, resolve before grading Q6 on it.

ahodroj         SQL surface over PyIceberg. No documented metadata or snapshot
                introspection tool.
                cites_version: NO, on the documented surface.

managed-spark   compute control plane; no table read surface at all.
                cites_version: NO.

Consequence for grading: Q6 scored 0 against a surface that cannot express a
version measures the surface's vocabulary, not the host. The right answer there
is a refusal that says so, which is the same measurement Q4/Q5 make on a server
with no row-returning tool.

## morristai/iceberg-mcp: declared vs served, measured 2026-09-16

Built from source and asked. `cargo install --git https://github.com/morristai/iceberg-mcp
--locked` produced iceberg-mcp v0.1.0 at commit 8ffb3b45, a 39.7 MB release
binary; the server identifies itself as rmcp 0.8.3.

Driven over stdio with initialize, notifications/initialized and tools/list:

  declared, in the project README   namespaces, tables, table_schema, table_properties
  served, by tools/list             get_namespaces, get_tables, get_table_schema,
                                    get_table_properties

The four capabilities match. **The names do not**: every served name carries a
`get_` prefix the documentation does not show. Anything keyed on the documented
names -- a scorer looking for a tool call by name, a config, a prompt that names
the tool -- would find nothing and report it as a tool that was never called.

`answers_rows: False` is unaffected and confirmed: none of the four returns rows.

Method note. The first probe piped the three requests in and got only the
initialize reply, because the server exits when stdin closes and did so before
answering tools/list. The trace showed it exactly -- three host->server frames,
one server->host frame, exit 0 -- which is what a frame log is for. Holding stdin
open returned the list.

## Correction to the 2026-09-04 availability check, measured 2026-09-16

The line above -- "mcp-iceberg-service  runnable via `uvx mcp-iceberg-service`;
uvx is present" -- is wrong, and was wrong when written. It records that uvx
exists, not that the package resolves. It does not:

  $ uvx mcp-iceberg-service
    x No solution found when resolving tool dependencies:
    '-> Because mcp-iceberg-service was not found in the package registry ...

`mcp-iceberg-service` is the GitHub REPOSITORY name. The package declares itself
`mcp-server-iceberg`, and neither name is published to PyPI (both 404). So the
server can only be run from git:

  $ uvx --from git+https://github.com/ahodroj/mcp-iceberg-service mcp-server-iceberg

which installs, and then dies at startup:

  AttributeError: 'IcebergServer' object has no attribute 'list_tools'

Its pyproject asks for `mcp>=1.0.0` with no upper bound, so uv resolves mcp
2.2.0, whose API no longer carries the decorator the server registers against.
`--with 'mcp<2'` is the obvious next thing to try and has NOT been tried here.

Confirmed three ways -- uvx directly, under claude, under codex -- so this is
ours and upstream's, not a finding about any host. It was found because the
control column failed identically, which is rule 1 in CLAUDE.md.

`missing_binary` did not catch it: for this server it resolves `uvx`, which is
present. The guard proves a launcher exists, not that a server starts. The only
check that would have caught this is an initialize + tools/list handshake, which
is what finally did.

The other stdio server, morristai/iceberg-mcp, starts and logs
"client initialized" against the same Polaris, so it is not affected.
