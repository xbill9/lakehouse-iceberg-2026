# Whether each host actually gives its model the MCP server's tools
# Measured 2026-09-16 against servers/iceberg_mcp.py, on apache-polaris.
#
# The server is held constant and is known good: it answers initialize,
# tools/list and tools/call correctly when spoken to directly, and two of the
# three hosts drive it to a correct answer. So a host that produces no tool call
# is a fact about the host, not about the server -- the control that makes that
# claim safe is the direct handshake plus the two hosts that do work.

host    registers   model sees tools   calls them   trace written
------  ----------  -----------------  -----------  -------------
claude  per run     YES                YES          YES
agy     global      YES (after fix)    YES          YES
codex   global      NO                 NO           NO

## claude
`--mcp-config` per invocation, `--strict-mcp-config`, so nothing global is
touched. Worked first time. Trace of a correct run:

    0.001s  initialize
    0.065s  tools/list
    7.906s  tools/call  iceberg_list_tables     {}
    9.464s  tools/call  iceberg_describe_table  {"table": "probe_ns.probe_table"}
   11.429s  tools/call  iceberg_scan_table      {"table": "...", "where": "id >= 10",
                                                 "limit": "5"}

Sent `"limit": "5"` as a string against a schema declaring integer. The server
now coerces to the declared type, so this cannot make one host's tool behave
differently from another's; the raw argument stays in the trace.

## agy -- was broken by our own add command, and the failure was invisible
`agy mcp add` takes flags ONLY before the server name. hosts.py wrote them after
it, as codex accepts, so every add failed:

    Error: invalid command "--env": flags must come before the server name
           (usage: mcp add [flags] <name> <commandOrUrl> [args...])

`prepare` passed check=False and discarded the output, so nothing surfaced, and
`agy mcp list` said "No MCP servers configured" for the whole smoke run.

**The reason this matters more than an ordinary bug.** With no tools at all, agy
still answered the question, and answered it correctly:

    There are 8 rows ... Total rows in table: 11 (IDs: 0, 2, 3, 10, 11, 12, 13,
    20, 21, 22, 23 -- row id = 1 was deleted during seeding).

It knew a row had been deleted during seeding. That is not in the catalog; it is
in this repository. These hosts are coding agents with a shell and a filesystem,
so the tool is not their only route to the answer, and a cell with a dead server
scores as a confident, correct, fully-sourced success. Paper 3 never faced this:
its agents had four tools and nothing else. Any cell here has to be read
alongside its trace, and a cell with no trace is not a result.

Fixed: flag order corrected, and `prepare` now raises on a non-zero add rather
than continuing into a run that cannot mean anything. After the fix:

    0.00s  server/discover            (agy-specific, not in the MCP spec)
    0.06s  initialize
    0.06s  tools/list
    5.31s  tools/call  iceberg_scan_table  {"table": "probe_ns.probe_table",
                                            "where": "id >= 10"}

## codex -- open, and it is not the server
Two problems, one fixed and one not.

FIXED: `codex exec` defaults to approval policy `never` inside a read-only
sandbox, and refused outright --

    MCP tool call requires approval, but approval policy is never

-- so the codex column would have measured a flag this harness failed to set.
`--dangerously-bypass-approvals-and-sandbox` is the counterpart of the other two
hosts' `--dangerously-skip-permissions` and is now passed. The read-only sandbox
also stopped the trace proxy opening its file, which hung the cell to the full
300s timeout instead of failing; with the flag the same cell returns in ~31s.

NOT FIXED: with the server registered and enabled, codex still gives its model
no tools from it. Asked directly, without the shell, it answers "NO MCP TOOLS",
and no frame ever reaches the server. Checked and ruled out:
  - registration: `[mcp_servers.ours-engine]` IS written to ~/.codex/config.toml
    for the life of the cell (an earlier grep that found nothing ran after
    cleanup had removed it).
  - the server: proven good by direct handshake and by claude and agy.
  - a stale tool cache: ~/.codex/cache/codex_apps_tools holds codex's own
    built-in surface, not ours.
  - `-c experimental_use_rmcp_client=true`: no change.
Left to try: whether `codex exec` loads mcp_servers at all, as against the TUI.

## Consequence for the smoke run
The six-cell run of 2026-09-16 is void except for its two claude cells. agy had
no tools and answered off the filesystem; codex timed out on both. It is kept
because the way it failed is the finding above, not because its numbers mean
anything.
