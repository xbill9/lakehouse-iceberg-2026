# Does moving the tools behind MCP change what the agent does?
# Measured 2026-09-16, apache-polaris control catalog, 24 runs.
#
# One leg, one question, two transports. Same framework, same model, same
# instruction, same four tools, same catalog. `agent.py` imports the tools into
# the agent process; `agent_mcp.py` reaches the same module through a server
# process over stdio JSON-RPC. The transport is the only variable.
#
# Questions are paper 3's, unchanged: one answerable from metadata, one needing
# a data read and a filtered count (8 of the 11 ids are 10 or more).

Three checks per run: the row count beside its noun, every column named, and the
version cited for the metadata question; the largest id, the filtered count and
the version for the scan question. Graded against
iceberg-mcp-hosts/evidence/ground-truth-apache-polaris.txt, read from the
catalog by pyiceberg.

## Result
Nothing moved. Every check passes on both transports, on both legs, on both
questions, and the medians differ by less than the spread within either column.

That is the useful shape of a null result here. The cost of MCP is not in what
the agent does -- it is in the code around the agent, which is measured
separately in mcp-per-framework.txt: three frameworks, three shapes of build(),
and a three-way branch in run_mcp.py that run_once.py never needed.

Strands on Nova Micro answers in two calls either way; ADK on Gemini takes
longer and is more variable on both transports, which is a property of the model
and the question, not of the transport -- the imported and MCP columns move
together.

## Scope
One catalog, local Polaris. Three runs per cell, which is enough to say the
columns match and not enough to put a number on the difference between them.
Two legs: the azure leg discovers its tools over MCP but wants
FOUNDRY_PROJECT_ENDPOINT to answer, so it is absent from this table rather than
scored.

Both transports are launched with the same environment, the catalogs file
pinned absolutely, and a run that ends in a launch or catalog error is recorded
as failed rather than scored -- a leg that could not start did not answer badly.
